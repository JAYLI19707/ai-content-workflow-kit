# Design Thinking for Codex Content Automation

这套结构的核心思想不是“把所有经验写成一份巨长提示词”，而是把内容自动化拆成稳定的工程层次。

第一层是根协作契约，也就是 `AGENTS.md`。它只回答一个问题：Codex 每次开始工作前必须知道什么。这里应该只保留高频、稳定、硬约束的信息，例如页数、真实性要求、LaTeX 模板不能乱改、输出结构必须固定。第二层是 `prompts/`，它们不是百科说明，而是针对具体任务的高价值指令资产，比如选题、单期生成、来源整理、LaTeX 精修。第三层是 `workflows/`，它把“怎么做”拆成可以复用的流程，而不是把所有工作塞进一次性 prompt。第四层是 `templates/`，它提供结构化输入输出，让 Codex 每次处理的信息更整齐。第五层是 `docs/`，专门放长文说明、迁移思路和维护原则，避免低频信息常驻污染上下文。这个拆法的本质是把高频和低频、规则和教程、输入和流程、创作和验收分开，从而让自动化更稳定。

对你这个项目来说，最重要的不是让 Codex“会写”，而是让它在正确的阶段看到正确的信息。比如“每一期 5–6 页、不要伪造真题来源、默认保留用户模板结构”这些必须常驻；而“如何维护整个内容流水线、以后怎么扩展选题池”这类内容可以放到 `docs/`。同样，面试题真实性校验和课程知识点映射，不能只靠主提示词顺手做完，最好单独拆出 `source-validation-workflow.md` 和 `source-log.md`，因为这两件事一旦混在正文生成里，就很容易出现措辞失真或者来源过度包装的问题。

换句话说，这套包借鉴的不是“文档越多越好”，而是“让模型在正确的时候，只看到刚好够用的信息”。这也是你上传文档里的核心思路：根契约应短、低频知识应下沉、工作流应复用、验证闭环必须独立出来。这里我只是把那套思路改写成更适合 Codex 做内容自动化的版本。
